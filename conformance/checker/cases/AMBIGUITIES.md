# checker.md: sentences found ambiguous, silent, or contradicted while writing the cases

Each entry quotes the sentence, gives the two readings, and names the reading taken and the cases that depend on it. The same list is in the P4 session report.

1. Item 92: "`expected.json` (per-step counts, final rows, descriptions, verdict)". No JSON shape is given, and the two hashes the task asks for are not in this list. Readings: any shape that holds those parts, or a fixed shape stated elsewhere. Taken: `{"verdict", "steps":[{"rows","description"}], "columns", "final_rows", "final_rows_hash", "key_map_hash"}`; an error case carries `"error":{"code","field"}` and `null` for the rest. Every case.
2. Item 92: eval `expected.json` holds "the 11.18.3 outcome or error", in "the case format `crates/tm-formats/README.md` gives", which is not available. Taken: `{"verdict"}` plus `"error":{"code","field"}` when the verdict is `error`. All 28 eval files.
3. 11.8: `"tables":{"de":"F7@v2"}` binds a name to a version handle, while a case directory holds `tables/*.csv` and `specs/*.json`. Nothing says how a name finds its file. Taken: name = file stem; the handle is a placeholder `F<i>@v1`. Every case.
4. 11.8 says "in key order" only for the `steps` null case; the order of a table before its first op is never stated. Readings: key order, or file order. Taken: key order, and every CSV is written in key order so both readings agree. empty_ops, nan_cell_fails, inf_cell_fails, every `value_*`/`compare_rows_*`/`count_gt` case with no ops.
5. 11.6: "Parsed values keep the scale as written, trailing zeros included" against "Decimal columns map to DuckDB `DECIMAL(38, s)` with `s` fixed per column". A `1.5` in a scale-3 column either stays `1.5` or comes back from DuckDB as `1.500`. Taken: as written, and every dec column is kept at one uniform scale so both agree; no derived dec passes through a DuckDB op.
6. 11.18.2 `select`: "Keeps the listed columns and the key columns" with template "Keep columns {cols}". Readings: `{cols}` is the list as written and the output keeps table column order, or `{cols}` is the resulting list with the key and the output follows the listed order. 7. 11.18.4 sort template: "`Sort by {col1} {dir1}, then {col2} {dir2}`" shows two entries, while "every other list is comma-separated with `, and ` before the last item when there are three or more". Readings: repeat `, then `, or apply the list rule. Taken: `, then ` repeated. sort_three_columns.
8. 11.18.4 group and join templates end their lists with "`, ...`". Readings: plain `, ` between items, or the list rule (` and ` for two, `, and ` for three or more). Taken: the list rule. group_min_max, group_three_aggregates, join_composite_on.
9. 11.18.1 `not := "not" not | cmp` makes the operand of `not` a whole comparison, and 11.18.4 emits "parentheses only where precedence requires them", so `not (fc > 1.0)` renders as `not fc > 1.0`. The other reading keeps the parentheses because `not` conventionally binds tighter than `>`. Taken: dropped. filter_not.
10. 11.18.2 `rank`: "`missing: first` or `last` assigns ranks as if sorted that way". Whether two missing rows tie (SQL `RANK` treats NULLs as equal) or are broken by key is not said. Taken: they tie. rank_two_missing_first.
11. 11.6: `nan`/`inf` are "treated as missing by filters and placed by the sort's missing rule". Silent on `rank`'s `missing` and on arithmetic with `inf` (11.18.2 says only "`nan` is `missing` for every operator"). Avoided: no rank over nan/inf rows and no arithmetic on inf.

16. 11.18.2 Domain: "Decimal overflow beyond 34 digits gives verdict `error` with `E5002`", while 11.6 says `int` is "arbitrary size", the named arithmetic (General Decimal Arithmetic at 34 digits) rounds rather than overflows, and division "otherwise rounds". ## Revised text (2026-11-17)

Items 1 to 31 above were ruled on in the revision. These are new.

32. 11.18.4: "`{cols}` lists the columns in the order the op writes them". For `select`, readings: the listed columns only, or the columns the op outputs, key columns included. 33. 11.18.2 Domain gives E5002 with verdict `error` but no `field`. The E6004 rule ("points at its `where` or `expr` member") covers only E6004. Taken: `/ops/<i>/expr`. derive_overflow_emax.
34. 11.7: `scale` is "the larger of the draft's and the largest scale seen", while "a scale-3 column accepts `0.001`, `0.0010`, and `1.0e-3`", and "`1.50e-2` counts as scale 4". Readings: trailing zeros count toward "scale seen", so table.spec would record 4 for that file. Or they do not, and it records 3. Taken: the spec is given at scale 3, so the case does not depend on which. exp_scale3_trailing_zero.
35. 11.6: "multiplication's scale is the sum of the operands' scales" against "`dec` results round to 34 significant digits". In derive_rounds_at_34_digits the sum rule gives scale 2 and the rounding gives scale 1. Taken: rounding wins, as Python `decimal` gives.
36. 11.6 and 11.18.1: a literal with an exponent "is converted exactly to positional notation", "`1e3` is `1000` (scale 0)". Python `Decimal("1e3")` keeps exponent +3. So `1.5 * 1e3` is `1500.0` if the literal is made positional before the arithmetic, and `1500` if it is not. Avoided: every new case uses negative exponents, where both readings agree.
37. 11.7: "in every other column such a token is `E3102` unless it is in the `missing` list". Read literally, this covers `str` columns, so a `str` cell holding `nan` or `Inf` would be refused. The likely intent is non-`float64` numeric columns. No case depends on it.

The `log` family row says "These six", adding `log2` and `log10`, and says the difference is "absorbed rather than tolerated". This was already there before the revision. No case depends on it.

## Underflow and the log family (2026-11-23)

43. 11.6 and 11.18.2 Precision: underflow "follows the specification (subnormal, then zero)", but the scale of such a result is not stated. The multiplication rule says the scale is the sum of the operands' scales. General Decimal Arithmetic rounds a subnormal result to exponent Etiny = Emin - (precision - 1) = -1000032 and gives an underflowed zero that exponent too. "Negative zero is written without its sign, scale kept" then makes the zero `0.` followed by 1,000,032 zeros, and the subnormal 1,000,034 characters. Readings: the scale is the General Decimal Arithmetic exponent, as Python `decimal` gives, or a zero is written `0`. Taken: the first, as in item 35 (rounding wins over the sum rule). derive_underflow_subnormal_then_zero; its expected.json carries both long strings.
Superseded by the decimal128 context (Emax 6144, Emin -6143).

## decimal128 context (2026-11-24)

44. 11.6 and 11.18.2 Precision: the context is "IEEE 754-2008 decimal128", whose format clamps (a result whose exponent is above Emax - (precision - 1) = 6111 has its coefficient padded with zeros down to exponent 6111; Python `clamp=1`), but the Python parameters the text lists are `prec=34`, `Emax=6144`, `Emin=-6143`, and `ROUND_HALF_EVEN`, which leave `clamp` at its default 0. Readings: clamp 0, as listed, or clamp 1, as decimal128 implies. Taken: clamp 0. No case depends on it: clamping changes only the exponent of an integral value, never the value, so the positional form (scale 0) and the Overflow threshold are the same under both; derive_overflow_emax gives E5002 and derive_underflow_subnormal_then_zero gives the same y and z under either reading.
Superseded: the Precision row now states clamp 0, with an example where the difference is visible.
