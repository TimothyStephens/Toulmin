# tm-record

The Record library (design 3, 11.3, 11.21; items 32 to 42): the main
chain in framed segments, `HEAD`, the lock with epochs and fencing, the
object store, event scans by position, and integrity checks. Journals
and the inbox are gate B and C APIs. The Record stores nothing derived
and never reads the index.

| Module | Item | What |
| --- | --- | --- |
| `layout` | 32 | `Record::create` (record.json, `main/` with the initial `HEAD`, `objects/sha256/`, `objects/tmp/`) and `Record::open`; a newer `record.json` format opens read-only |
| `segment` | 33 | `seg-NNNNNN.jsonl` and `.zst`, the batch header, the frame walk, sealing at zstd level 9 with checksum and read-back, resumed sealing |
| `head` | 34 | `HEAD` read with a directory refresh, write-then-rename, the lock re-read before the rename (11.21 step 3) |
| `lock` | 35 | `O_EXCL` lock, in-place heartbeat through the original descriptor, epoch to `HEAD` first, takeover after a stale heartbeat on the monotonic clock, torn-tail truncation at acquisition, `break_lock`, `lock_status` |
| `objects` | 36 | `keep` (stream through SHA-256 and zstd level 3, `E3203` on mismatch), `open_object`, `objects` |
| `scan` | 37 | `events`, `events_after`, `events_of_type`, `read_at(Position)`, and `find_by_id` as a linear scan |
| `verify` | 38 | `verify() -> Vec<Finding>`: one `FindingKind` per item 41 case plus `head_field_mismatch`; empty is clean |
| `append` | 39 | `Batch::new` over lines, `Batch::build` over known events, `Record::append(&Lock, &Batch)` with the 3.1 fencing re-read |

`Record::append(&OwnerCap, &Lock, &Batch)` is the main-chain write of rule
4; the capability comes from `tm-owner-cap` and only `tm-cli` constructs
it. The crate's own tests (`src/lock_tests.rs`, the unit tests) and the
generator (`src/gen_chain.rs`, behind the `gen-chain` cargo feature that
the crate's own tests and example enable, so the library's consumers
never see it) append through the crate-private path behind it, so no
test names the constructor.

## Conformance cases (`conformance/record/`)

Generated by `cargo run -p tm-record --features gen-chain --example gen-chain -- --conformance conformance/record`
with a 2500-byte segment limit so packed segments appear; the generator
is deterministic (fixed times, IDs, and bodies), so a second run changes
nothing. `tests/record_conformance.rs` runs them.

| Directory | Holds | `expected.json` |
| --- | --- | --- |
| `chains/<name>/record/` | A complete record directory | `events`, `batches`, `segments` (`segment`, `form`, `batches`), `head` (the `HEAD` object), `positions` (`[segment, offset, id]` per event), `types`, `objects`, `lock` (the holder or `null`), `findings` (empty) |
| `tamper/<case>/record/` | A record with one item 41 tampering applied | `findings`: the case's own name, once |

The eight tamper cases are item 41's: `kept_byte_changed`,
`segment_line_removed`, `segment_byte_changed`, `batch_hash_mismatch`,
`torn_tail_beyond_head`, `fork_prev_mismatch`, `head_offset_mismatch`,
`packed_segment_corrupt`. `verdict_data_changed` is item 82's.

## Tests

- `cargo test -p tm-record`: unit tests (including `src/lock_tests.rs`:
  two processes contend; a paused holder is fenced out after a takeover;
  two waiters split the rename and the create; a crash after a seal) and
  `tests/record_conformance.rs`.
- `cargo test -p tm-record --lib -- --ignored nfs` with `TM_NFS_DIR` set
  to a directory on the CI NFS loopback mount runs the two contention
  cases there.
- `cargo run -p tm-record --features gen-chain --example gen-chain -- --events 1000000 --out DIR`
  writes the chain `bench-index.sh` rebuilds from (P7).
