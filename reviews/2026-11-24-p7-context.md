## Verdict

**Merge. Nothing blocks.**

All seven checks hold except one part of check 6, the citation. The two
new formats cases name ruling 56. The checker cases name it only in a
commit subject: their NOTES.md entries say "re-derived for the decimal128
context", because NOTES.md never cites a ruling number (`checker.md`, the
case writer's only source, has none).

Three issues fall outside the checks, and none was introduced by this
branch:
- **A.** Python runs the literal-range check in the shape pass and Rust in
  the spec pass. When a case has a second fault, the two report different
  errors.
- **B.** The Python reference crashes on a literal whose exponent has 19 or
  more digits. Rust gives `E6004`.
- **C.** `int` stays unbounded under ruling 16, so a hashed record can
  still hold a million-digit value.

A and B each need a `checker-diffs.md` entry for the owner to rule on. C is
covered by recorded rulings (16 and 56), so I note it and do not reopen it.

## Check 2: the two contexts and the literal-range checks match the design

Holds for the context and for which literals are refused. [Certain]

- **Rust.**
  - `EMAX` is 6144 and `EMIN` -6143 (`tm-formats/src/expr.rs:204-206`).
  - `PREC` is 34, `ETINY` -6176, and `ETOP` 6111
    (`tm-checker/src/eval.rs:30-34`).
  - I compared `fix` (eval.rs:107) branch by branch with CPython's
    `_pydecimal.Decimal._fix`:
    - a zero's exponent is clamped to [Etiny, Emax], the clamp-0 bound;
    - Overflow is `exp_min > Etop`, which is the same as adjusted > Emax;
    - subnormal rounding stops at Etiny;
    - a carry to 35 digits moves the exponent up one;
    - there is no fold-down step, so a non-zero result above Etop comes
      back unchanged.

    That is clamp 0, as the Precision row now states.
  - The `decimal128_limits` test (eval.rs:655) pins Etiny, the overflow at
    9.9e6145, the subnormal 1E-6173, and zero at Etiny.
- **Python.**
  - `typed_values.CONTEXT` (line 24) prints as prec 34, Emax 6144, Emin
    -6143, `ROUND_HALF_EVEN`, clamp 0, Etiny -6176, Etop 6111, traps
    `[Overflow]`.
  - Clamp is not passed explicitly. It comes from `DefaultContext`, which
    nothing in `reference/` changes, and the Precision row says the same
    ("Python `decimal`'s default").
  - All arithmetic names `CONTEXT` or `EXACT` explicitly; none uses the
    thread context.
- **Literal range.** Both implementations refuse every `INT`, `DEC`, and
  `EXPNUM` whose adjusted exponent (as `Decimal.adjusted` gives it) lies
  outside [-6143, 6144], with `E6004` at the `where` or `expr` member:
  - Rust in `check_literal_range` (expr.rs:228), which `type_of` (718)
    calls for every numeric literal;
  - Python in `number_literal` (exprs.py:239), which since f8a6af8 covers
    all three forms.

  Probing the Python side: `a > 9.9e6144` and 6,145 nines are accepted.
  `1e6145`, 6,146 nines, and `0.` followed by 6,143 zeros and then `1` all
  give `E6004`.
- When the error is reported is a separate matter; see A.

## Outside the checks (not blocking)

### A. The two implementations run the literal-range check in different passes

- **Python** raises `E6004` while parsing, and it parses in the shape pass
  (`ops._expression`, line 121).
- **Rust** parses in the shape pass without a range check
  (`steps.rs:188`). It checks the range only inside `type_of`, which runs
  in the spec pass (`check_op`, `steps.rs:571`). In that pass a `derive`
  checks its `as` before its `expr` (619-626).
- When a case has a second fault, the two report different errors. Python
  column [Certain], Rust column [likely]:

  | Case | Python (ran) | Rust (read from the code) |
  | --- | --- | --- |
  | `x < 1e6145 +` | `E6004` `/ops/0/where` | `E6006` `/ops/0/where` |
  | `x < 1e6145`, then a `sort` with no `by` | `E6004` `/ops/0/where` | `E6002` `/ops/1/by` |
  | `nope < 1e6145` | `E6004` `/ops/0/where` | `E6005` `/ops/0/where` |
  | `derive`, `as` `x` (already present), `expr` `x * 1e6145` | `E6004` `/ops/0/expr` | `E6002` `/ops/0/as` |

- **History.** The difference dates from ruling 36, for `EXPNUM`.
  f8a6af8 extends Python's parse-time check to `INT` and `DEC` without
  moving it. The branch neither causes the difference nor widens it.
  Before it, an out-of-range `INT` crashed Python outright.
- **Which side the design favours.** 11.8 (line 845) says "Checks that need
  no parse spec are made wherever steps are read". It lists `E6005`, the
  operand types, and the join cover as the spec checks, and the range
  check needs no spec. D13 settled a similar case (shape against schema) in
  favour of the shape check, with Rust changing. So 11.8 reads in Python's
  favour; the ruling is the owner's.
- The generator does not reach this: its out-of-range literal sits in an
  otherwise valid pipeline.

### B. The Python reference crashes on a literal with a 19-digit exponent

- For `x < 1e99999999999999999999`, the `Decimal(text)` call in
  `number_literal` raises `decimal.InvalidOperation`: the exponent is past
  libmpdec's `MAX_EMAX`. `refcheck.py` exits 1. [Certain, ran]
- Rust gives `E6004`; `tm-formats` asserts this at `expr.rs:974`.
- This predates the branch, which only moved the call above the `EXPNUM`
  branch.
- It is the same class as the three int-string rulings: Python raises
  where Rust gives a code. The fix would be the same kind: check the
  exponent on the text first, or map `InvalidOperation` to `E6004`.

### C. `int` stays unbounded, so ruling 56's purpose holds for `dec` only

- Ruling 56's reason is that a hashed record must not hold a million-digit
  value. Decimal128 limits a computed `dec` to about 6,200 characters.
- Two kinds of value stay unbounded: a computed `int` (ruling 16), and an
  `int` that `coalesce` widens to `dec`, which both implementations widen
  exactly.
- On the Python reference I ran eight chained derives from one 38-digit
  cell (`y1 = x * x`, then `y{k} = y{k-1} * y{k-1}`) and then a `group` on
  `y8`. The group's `by` value was a 9,728-digit `int`. [Certain, ran]
- A group's `by` tuple is its key tuple (11.18.2 Key mapping), and
  `claim.checked` writes `key_map` in full (11.16). Fifteen derives would
  put about 1.2 million digits into a hashed record.
- Rulings 16 and 56 cover this ground and are recorded, so I neither
  reopen nor count it. The owner may want to know before P7 writes the
  first record.
